Your questions, answered

In the README: what does "scheme http or https" mean? Non-empty host? Not fetched to check it resolves?

Take a web address apart:

https://www.digitalocean.com/products/app-platform
^^^^^   ^^^^^^^^^^^^^^^^^^^^ ^^^^^^^^^^^^^^^^^^^^^^
scheme  host                 path
  • Scheme is the part before ://. It says how to talk to the address. We only accept http and https, so things like ftp://, mailto: or javascript: are refused. The last one matters: a shortener that redirects to javascript: would run code in the visitor's browser.
  • Host is the domain name, www.digitalocean.com. "Non-empty host" means https:// on its own, with nothing after it, is refused.
  • Not fetched to check it resolves means: we do not visit the address to see whether it actually exists. We only check that it is shaped like an address. Two reasons. Visiting it would make every create request slow and dependent on some other website being up. And it would let anyone make our server send requests to any address they choose, including addresses inside our own network. That trick has a name, SSRF, and it is a classic security hole.

Short version for the review: "I validate the shape of the URL, not whether it works. Checking whether it works is slow and is a security risk."

What is a browser visitor? Someone trying to access the shortened link from their browser?

Yes, exactly. The diagram has two kinds of client because they behave differently:

  • API client: a developer, a script, or our own web page, sending JSON to create, read, or delete links. They understand JSON replies.
  • Visitor: anyone who clicks a short link. They are a person in a browser. They never send JSON and never see any. They type or click …/launch, the browser gets told "go over there", and it goes. The visitor does not know our service exists.

The distinction matters for the design: the redirect route must be public and must answer with a redirect that browsers follow automatically, while the API routes answer with JSON for programs.

Does the DigitalOcean deployment depend on GitHub Actions passing the tests? Are there unit tests and integration tests? Should there be? Do deployments depend on them passing?

Does the deploy wait for the tests? Yes, as of the last change. It did not originally: they ran side by side. A push to main tells GitHub Actions to run the tests, and separately tells App Platform to build and deploy. Neither waits for the other. If a test failed, the deploy would still go out.

This was a gap for most of the day and was closed at the end: App Platform's deploy-on-push is now off, and the workflow has a deploy job that runs only on main, only after both test jobs and the image build succeed, and triggers the deployment with doctl using an API token stored as a GitHub secret. A failing test now stops the deploy.

What protects production today? The health check. If the new container does not answer /healthz, App Platform keeps the old one running. That caught every failed deploy today. But it only catches "crashes on startup", not "a test would have failed".

Unit versus integration. Almost all 47 tests are integration tests: they send a real HTTP request through the whole app, from the route down to a real database, and check the reply. Only one is a unit test, the one that builds an old-format SQLite file and checks the storage layer upgrades it. That balance is deliberate. For a service this small, testing through the front door proves the most with the least code. If the link layer grew complicated, I would add unit tests for it on its own.

Short version: "A push deploys only if CI is green. Then the health check gates traffic. Two gates: tests before the build, health check before traffic."

What is "managed Postgres"? Why is it in the deploy diagram? Is it the same as the dev database? Should it be renamed?

Postgres is a database program. Managed means DigitalOcean runs it for you: they install it, keep it running, patch it, and hand you an address and a password. You never touch the server it runs on. The alternative is running Postgres yourself on a machine you maintain.

The dev database is managed Postgres. Same thing, smallest size. DigitalOcean sells managed Postgres in tiers. "Dev database" is the cheapest tier, meant for development: one small instance, no backups, no standby copy, and you cannot change permissions yourself (which is the wall we hit today). The production tiers add backups, a standby that takes over if the main one dies, and more capacity.

Why it is in the deploy diagram: the diagram shows what runs where. Containers come and go with every deploy; the database is a separate thing that persists across them, and every container connects to it. Leaving it out would hide the most important piece of the "why does data survive a redeploy" story.

Rename? Not necessary, but "Managed Postgres (dev tier)" would be more precise. The README already says in the deploy section that it is the dev tier and why.

What does the "307, not 301" thing mean? Is that an error message?

Not an error. They are two kinds of "go somewhere else" reply. Every HTTP reply carries a three-digit status number. The 300s all mean "what you want is at a different address":

  • 301 means "moved permanently, remember this". A browser that sees a 301 caches it. Next time the user clicks the same short link, the browser skips us entirely and goes straight to the destination. We never see that click.
  • 307 means "go there for now, ask me again next time". Every click comes through us.

Since the whole point of the metadata is the click count, we need every click to come through. So 307. The cost is one extra round trip per click, a few milliseconds.

For contrast, the numbers that are errors: 404 (no such link), 409 (that alias is taken), 410 (that link expired), 422 (your input is wrong). And 2xx means success: 200, 201 created, 204 done with nothing to return.

I kinda get why there are two backend databases, in case Postgres fails. But what happens if it fails? How do they reconcile when Postgres comes back?

That is not what the two backends are for, and it is worth being precise here because a reviewer might probe it. They are not a failover pair. Nothing switches between them and nothing reconciles.

The two backends exist for two different environments:

  • SQLite for your laptop and for the tests. Zero setup, a file appears, tests run in a fifth of a second.
  • Postgres for production, where several containers need to share one set of data that survives redeploys.

A running container uses exactly one of them, chosen once at startup by whether DATABASE_URL is set. It never changes its mind while running.

So what happens if Postgres goes down in production? Requests that need the database fail. The connection pool throws, the request logs a 500 with a traceback, and the visitor gets an error. If a container restarts while Postgres is down, it fails at startup, and App Platform keeps the old container (which will also be erroring, but at least it is up). The service is down until Postgres is back. When Postgres comes back, the pool reconnects on the next request and things resume. There is nothing to reconcile because nothing was written anywhere else in the meantime.

Is that acceptable? For this exercise, yes, and it is the normal answer: the database is the thing you make highly available, not something you fail over to a local file. The production tier of managed Postgres includes a standby copy that takes over automatically. Falling back to SQLite would be worse than failing: two containers would silently write to two different files, and you would have exactly the data-splitting bug from earlier today, plus the mess of merging it later.

Short version: "SQLite is for dev and tests, Postgres is for production. If Postgres is down, the service is down, and the fix for that is a production database tier with a standby, not a local fallback."

Where does Pydantic do the validation?

In app/models.py, and it happens before the route function runs.

The route in app/main.py is declared like this:

def create_link(body: CreateLinkRequest, request: Request) -> LinkResponse:

That type annotation, body: CreateLinkRequest, is the instruction. When a request arrives, FastAPI reads the JSON and tries to build a CreateLinkRequest from it. Pydantic is the library that does the building. In the process it:

  1. checks the field types: long_url must be a string, expires_at must parse as a date, missing required fields are an error;
  2. checks the built-in constraints, like max_length=2048;
  3. runs our custom validators, the functions in models.py marked @field_validator: the URL scheme and host check, the alias rules (which call into codes.py), and the expiry-in-the-future check.

If any of that fails, Pydantic raises an error, FastAPI catches it, and our handler in main.py turns it into 422 {"error": "field: message"}. The route function never runs. If it all passes, the route receives a body object whose fields are already the right types and already checked.

That is why the route can be three lines: by the time it runs, there is nothing left to check.
