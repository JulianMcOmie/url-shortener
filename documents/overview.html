The URL shortener, explained

What it does, how it does it, and where each piece lives in the code. No prior knowledge assumed.

1. The idea: a coat check for links

Long web addresses are ugly and hard to share. You hand this service a long address, it hands you back a short ticket. Anyone who uses the ticket gets sent to the long address. The service also remembers how many times each ticket was used.

2. What "a REST API service" means

A service is a program that runs all day on a computer somewhere and waits for messages. An API is the list of messages it understands. REST is just the common style for those messages: each one is a verb plus an address, and the reply is a status number plus some data.

This service understands five messages. That is the whole menu:

MessageIn plain wordsGood replyBad replies
POST /v1/links"Shorten this address for me." Optionally: "and call it launch" or "and make it expire on Friday."201, here is your link422 your input is wrong · 409 that name is taken
GET /mHlophd"Take me where this ticket points."307, go over there404 no such ticket · 410 this ticket expired
GET /v1/links/mHlophd"Tell me about this ticket." (Does not count as a visit.)200, here are the details404
DELETE /v1/links/mHlophd"Tear up this ticket."204, done404
GET /healthz"Are you alive?" DigitalOcean asks this every few seconds.200, yes
Why the numbers? Status numbers are a shared language. 2xx means it worked, 4xx means the request was the problem, 5xx means the service was the problem. A browser or another program can act on the number without reading the words.

3. How the code is organised: four counters in a row

The code is split into layers. A request walks past each one in order. Each layer has one job and only talks to its neighbours. Think of a restaurant: the host takes your order, the kitchen cooks it, the pantry holds the ingredients. The host never touches the pantry.

Why bother with layers? Each layer can be tested, understood, and replaced on its own. Swapping the database (which we did, see section 7) touched only the bottom layer.

Why 307 and not 301? Both mean "go there." But 301 means "permanently, and remember that," so a browser stops asking us and goes straight to the destination next time. We would never see those visits, and the count would be wrong. 307 means "for now," so every click comes through us.

6. Story: when the input is wrong

Bad input is normal. The job is to refuse it clearly. Every error this service returns has the same shape: a status number and one sentence naming the field that is wrong.

catcher · app/main.py
Same shape for those, and for the framework's own "no such page."

Why one shape? Whoever writes a program against this API only has to handle errors one way. And "the field named X is wrong because Y" is something a person can act on; a bare 422 is not.

A database is a spreadsheet that many programs can write to at the same time without stepping on each other. This service has one sheet.

The code column is the primary key: the database guarantees no two rows share one. That single rule is what makes "alias already taken" and "random code collided" detectable without any extra code.

Two ways to keep that sheet

This bit us for real. The first deployment ran two containers, each with its own SQLite file. A link created on one was unknown to the other, so about half of all clicks got a 404. The fix was Postgres. The code change was small because only the bottom layer knew about the database.

8. Knowing what is going on

Once the service is running far away, you cannot watch it. Two things stand in for your eyes.

A diary: one line per request

Every request writes a single line: what was asked, what was answered, and how long it took. DigitalOcean collects these lines and shows them in the console. If something is slow or failing, this is where you look first.

one log line, as it appears in Runtime Logs{"time": "2026-09-22T19:40:12Z", "level": "INFO", "logger": "app.request", "message": "request", "method": "GET", "path": "/launch", "status": 307, "duration_ms": 1.4}
app/observability.py
Wraps around every request like a stopwatch.
async def log_requests(request: Request, call_next)
app/observability.py
Formats each line as JSON so tools can search it, with times in UTC.
class JsonFormatter(logging.Formatter)

A pulse: "are you alive?"

DigitalOcean calls /healthz every few seconds. If a container stops answering, traffic is moved away from it. It also tells you which ledger that container is using.

app/main.pydef healthz(request) -> dict # {"status": "ok", "storage": "postgres"}

11. From my laptop to the internet

Saving code to GitHub sets two things in motion at once: the robot runs the tests, and DigitalOcean builds and starts a fresh copy of the service.

Why is this "production-ready thinking"? Nobody copies files to a server by hand. The path from a change to a running service is automatic, the same every time, and guarded by tests and a health check. A bad change cannot take the site down; it just fails to deploy.

12. Words used above

Container
A sealed box holding the program and everything it needs. Runs the same anywhere.
Endpoint / route
One entry on the API menu: a verb plus an address, like GET /healthz.
JSON
The text format for the data in requests and replies. Curly braces, quoted names, values.
Redirect
A reply that says "go to this other address instead." Browsers follow it automatically.
Primary key
A column the database keeps unique. Here it is code.
Environment variable
A named setting handed to the program at startup by whatever runs it.
CI
Continuous integration: tests that run automatically on every change.
Health check
A tiny request the platform sends repeatedly to see if the service is alive.
Rollback
Keeping the previous version running because the new one failed to start.
